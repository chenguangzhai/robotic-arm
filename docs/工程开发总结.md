## 1. 项目概况

| 项 | 内容 |
|---|---|
| 主控 | STM32F103C8T6（72MHz，64KB Flash，20KB RAM） |
| 框架 | STM32 HAL + CubeMX 生成 |
| 构建 | CMake（`2.0/CMakeLists.txt`，**显式列源文件**） |
| 自由度 | 底座偏航 + 肩 + 肘 + 腕（4 轴）+ 夹爪旋转 + 夹爪开合 |
| 末端控制 | 笛卡尔坐标 `(x, y, z)`，单位米 |
| 输入通道 | 4 个按键 + 串口指令 + 网页上位机 |

### 版本关系

- **`1.0/`** — 完整可用：三连杆逆解、按键控制 x/y、OLED 实时显示。**没有串口解析**。
- **`2.0/`** — 在 1.0 基础上加：串口协议层、运动控制模块、夹爪/旋转、标定补偿。
- **`3.0/`** — 在 2.0 基础上加：**关节空间示教 / 回放**（`Hardware/Play/`），
  点表可存 Flash 掉电不丢，网页端有示教面板。

> ⚠️ 上位机只能连 `2.0/` 或 `3.0/`。发指令给 `1.0/` 不会有任何反应（字节只躺在缓冲里）。
> 3.0 的网页能识别 3.0 的 T/L/P 等指令，2.0 的网页没有示教面板。

## 2. 硬件配置

### 2.1 引脚映射

来源：`Core/Src/tim.c` 的 `HAL_TIM_MspPostInit()`。

| 舵机 | 功能 | 定时器通道 | 引脚 |
|---|---|---|---|
| 1 | 底座偏航 | TIM2_CH1 | **PA0** |
| 2 | 肩（大臂） | TIM2_CH2 | **PA1** |
| 3 | 肘（小臂） | TIM2_CH3 | **PA2** |
| 4 | 腕 | TIM2_CH4 | **PA3** |
| 5 | 夹爪**旋转** | TIM3_CH1 | **PA6** |
| 6 | 夹爪**开合** | TIM3_CH2 | **PA7** |

**其他占用**

| 功能 | 引脚 | 说明 |
|---|---|---|
| USART1 TX/RX | PA9 / PA10 | 115200 8N1，接 USB-TTL |
| OLED SCL/SDA | PB8 / PB9 | 软件 I2C |
| 按键 Key1~4 | PA11 / PA12 / PA15 / PB3 | 低电平有效 |
| LED | PC13 | |
| SWD | PA13 / PA14 | 下载调试 |

> **PA15 / PB3 是 JTAG 引脚**，靠 `__HAL_AFIO_REMAP_SWJ_NOJTAG()` 释放成 GPIO。
> `Key.c` 已改为引用 `main.h` 的 `KEYx_Pin` 宏，CubeMX 改引脚后不用再动 `Key.c`。

### 2.2 PWM 参数

TIM2 / TIM3 完全一致：

```
PSC = 71, ARR = 19999
72MHz / (71+1) / 20000 = 50Hz
脉宽 500~2500us 对应 0~180°
```

换算：`CCR = 2000 × angle / 180 + 500`

### 2.3 机械参数

唯一来源：`Servo_motor.c` 的 `mech_length`（单位米）。

| 符号 | 含义 | 值 |
|---|---|---|
| `l0` | 底座立柱高度 | 0.08 |
| `l1` | 肩 → 肘 | 0.10 |
| `l2` | 肘 → 腕 | 0.09 |
| `l3` | 腕 → 末端 | 0.17 |

总伸展 0.36m。实测连杆总长约 35cm，代码取 36cm，差 1cm 在容差内。

### 2.4 舵机行程限制

`Servo_motor.c` 的 `SERVO_MIN` / `SERVO_MAX`：

```c
SERVO_MIN = {  0,   0,  45,   0,   0,   0};
SERVO_MAX = {180, 180, 180, 180, 180, 180};
```

**只有肘（舵机 3）下限是 45°**，其余 0~180。

### 2.5 接线要点

**USB-TTL 接板子**

| USB-TTL | STM32 | 说明 |
|---|---|---|
| TXD | PA10 | 模块发 → 板子收，**要交叉** |
| RXD | PA9 | 板子发 → 模块收 |
| GND | GND | **必须共地**，不接必乱码 |

**舵机供电**

> ⚠️ 舵机电源**不要**从板子的 5V 取。6 路舵机同时动作，堵转电流可达数安培，
> 会直接把板子电压拉垮，表现为单片机复位、OLED 花屏、舵机抖动。
> 用独立 5V 电源（≥2A）供电，**GND 必须和板子连在一起**，否则信号没有参考电平。

## 3. 软件架构

### 3.1 分层

```
┌─────────────────────────────────────────────┐
│  main.c    主循环：按键 + 串口汇成同一份目标   │
├─────────────────────────────────────────────┤
│  protocol.c  切行 + 解析 + 分发（不驱动舵机）  │
├──────────────────────┬──────────────────────┤
│  motion.c            │  play.c              │
│  沿直线按时间推进      │  示教点 / 关节插值回放 │
│  （笛卡尔，要逆解）    │  （关节空间，不做逆解） │
├──────────────────────┴──────────────────────┤
│  model.c     逆运动学 + 正解（只算角度）       │
├─────────────────────────────────────────────┤
│  Servo_motor.c  舵机角度 → PWM 脉宽            │
├─────────────────────────────────────────────┤
│  uart_app.c  环形缓冲 + DMA，只搬字节          │
└─────────────────────────────────────────────┘
```

**每层不知道上层/下层内部**：

- `uart_app.c` 不知道什么叫"命令"，只搬字节。
- `protocol.c` 不知道 DMA 怎么工作，也不驱动舵机。
- `motion.c` / `play.c` 不知道命令从哪来，两者互斥（回放期间 `M` 回 `ERR:BUSY`）。
- `play.c` 只往上依赖 `model_fk` 和 `Motion_SyncFromCurrent`，不反向依赖。
- `model.c` 不知道舵机怎么接线。

**收益**：加一条输入通道（串口/蓝牙/WiFi）时，执行层零改动。

### 3.2 主循环调用顺序

```c
while (1)
{
    Protocol_Poll();      // 串口命令 → 改目标 / 记录点 / 启停回放（非阻塞）
    // 按键 → Motion_SetTarget()（回放期间只读不执行）
    Motion_Tick();        // 按时间推进一次
    Play_Tick();          // 回放时按关节插值推进；没在回放就一句判断
    // OLED 刷新（运动/回放中跳过区间扫描）
}
```

### 3.3 构建注意

`2.0/CMakeLists.txt` 是**显式列源文件**，不是 glob。

> 新增 `.c` 必须手动加进 `target_sources` 和 `target_include_directories`，
> 否则编译报 `undefined reference`。
>
> 3.0 加的是 `Hardware/Play/play.c` 和对应 include 目录 `Hardware/Play`。

## 4. 逆运动学

实现：`Hardware/Servo_motor/model.c`

### 4.1 坐标约定

| 轴 | 含义 | 说明 |
|---|---|---|
| `x` | **正前方**水平距离 | 底座朝向为 +x |
| `y` | **离地高度** | ⚠️ 不是"前后"，是竖直方向 |
| `z` | 水平面内**横向**偏移 | 与 x 垂直 |

> 这个约定容易混：`y` 是高度，不是通常的"纵深"。画图/调试时特别注意。

### 4.2 模型：三连杆 3R

俯仰平面内是标准三连杆（肩、肘、腕），末端位置只有 `(r, h)` 两个约束，
而关节有 3 个 → **多出 1 个冗余自由度**。

处理方式：**放弃对姿态角 α 的约束**，用冗余自由度去挑「|α| 最小」的解。

```
从 α = 0（夹爪水平）出发，向两侧逐步放宽（步长 5°）
第一个可行姿态即为答案
→ 能水平就水平，够不到才倾斜
```

这比锁死腕关节的工作空间大得多。

### 4.3 肘上 / 肘下双构型

余弦定理只能给出 `|th2|`，肘上（`+th2`）和肘下（`-th2`）都能到达同一点。
代码两个都试。

> 实物是**肘下**工作。早期只试肘上，导致大量本可达的点被误判 OUT。

### 4.4 舵机标定

映射关系：`a = ZERO + DIR × th_deg`

| 关节 | 几何零位定义 | ZERO | DIR |
|---|---|---|---|
| 肩 a1 | 大臂向前水平 | 180 | −1 |
| 肘 a2 | 小臂与大臂成直线 | **178** | +1 |
| 腕 a3 | 夹爪与小臂同轴 | 90 | −1 |

**肘的 ZERO 是 178 而不是 180**：实物所有姿态都恒定比目标高约 2°，
把零位减 2 做全局补偿。改这里就够，不用动别处。

> 若实测偏差不是 2°：偏高 1.5° → 178.5，偏高 2.5° → 177.5。
> 若补偿过头（变成偏低），往 180 方向回调。

**腕的 ZERO 是 90**：`a3 = 90` 时夹爪与小臂同轴。

### 4.5 验证结果

| 指标 | 结果 |
|---|---|
| IK → FK 闭环误差 | **0.0000 mm**（6669 个可达点） |
| 参照点 (0.36, 0.08) | 解出 S180 E180 W90（全伸直，与实测一致） |
| 可达率 | **66.3%** |

> 可达率 66.3% 的扫描范围：`x ∈ [0.05, 0.40]`、`y ∈ [0.02, 0.42]`、
> `z ∈ {-0.10, 0, 0.10}`，步长 10mm。
> **换扫描范围数字会变**，对比时务必用同一范围。

**典型点解算结果**

| 目标 | B | S | E | W |
|---|---|---|---|---|
| (0.28, 0.10, 0) | 90 | 120 | 69 | 42 |
| (0.30, 0.10, 0) | 90 | 128 | 85 | 49 |
| (0.36, 0.08, 0) 全伸直 | 90 | 180 | 178 | 90 |
| (0.24, 0.14, 0) | 90 | 84 | 56 | 64 |
| (0.28, 0.10, 0.10) | 127 | 127 | 87 | 48 |

### 4.6 底座偏航

```
waist = atan2(z, x) × 180/π + 90
```

- `z = 0` → `waist = 90°` → **正前方**
- `z > 0` → 右偏
- `z < 0` → 左偏

**舵机 0~180° 只覆盖 `x ≥ 0` 的半平面**（正前方左右各 90°）。
`x < 0`（目标在背后）物理上到不了，`solve()` 里会直接判不可达。

**z 可以负，且与 z 正完全镜像对称**——俯仰解算只看 `r = hypot(x,z)`，与符号无关。

| 固定 | z 最小可达 | 对应偏航 |
|---|---|---|
| x = 0.20 | −0.295 m | −55.9° |
| x = 0.28 | −0.225 m | −38.8° |
| x = 0.34 | −0.115 m | −18.7° |

极限是**连杆总长**卡的，不是偏航角卡的。

## 5. 串口协议

实现：`Hardware/UART/Protocol/protocol.c`

### 5.1 指令表

| 指令 | 说明 |
|---|---|
| `M x y z` | 移动到 `(x,y,z)`，单位**米**。回 `OK` 表示**已受理**，到位时推 `DONE` |
| `Y <度>` | **3.1** 纯偏航：锁定当前半径与高度，只转底座，范围 ±88°。见 6.6 |
| `G 0\|1` | 夹爪开合：`0` = 张开（0°），`1` = 收紧（60°）。只驱动 PA7 |
| `R <角度>` | 夹爪旋转 0~180°。`0` = 平行地面，`60` = 垂直地面（**实测**，见 [7.3](#73-旋转)） |
| `V <mm/s>` | **3.0** 设置末端巡航速度，20~150mm/s，回 `OK <mm/s>`。`S` 是别名 |
| `T [ms]` | **3.0** 把当前 6 个关节角记成一个示教点，停留时间默认 500ms |
| `A a1..a6 [ms]` | **3.1** 追加一个**指定角度**的点（0~180），不读当前姿态。给上位机推回缓存用，见 [8.6](#86-点表存在哪里31) |
| `L` | **3.0** 列出点表：每点一行 `L <序号> <6 个角> <停留>`，末行 `L END <总数>` |
| `P [遍数]` | **3.0** 回放，不带参数 = 无限循环。每点推 `PLAY i/n`，结束推 `PLAY END` |
| `X` | **3.0** 停止回放（停在当前姿态） |
| `D <序号>` | **3.0** 删除第几号点（1 基，与 `L` 的序号一致） |
| `C` | **3.0** 清空点表（只清 RAM，不擦 Flash） |
| `W` | **3.0** 点表写进 Flash，上电自动载入 |
| `?` | 查询状态 |

参数之间空格、Tab、逗号都行；结尾 `\n` 或 `\r\n` 都行；大小写均可。

### 5.2 状态应答

```
S <x_mm> <y_mm> <z_mm> <底座> <肩> <肘> <腕> <夹爪> <旋转> <busy>
```

固定 **11 个字段**，按空格 split 后按位置取值。

- 坐标是**整数毫米**（不用 `%f`，见 [9.4](#94-不能按-idle-切帧)）
- 角度是 `NewAngle`（目标值），不是插值中间值
- `busy = 1` 表示还在运动，应等 `DONE` 再发下一条 `M`

### 5.3 错误码

| 错误码 | 含义 |
|---|---|
| `ERR:CMD` | 无法识别的命令字 |
| `ERR:ARG` | 参数个数不对或不是数字 |
| `ERR:RANGE` | 坐标/角度/速度超范围（多半是单位笔误，把毫米当米） |
| `ERR:OUT` | 目标点超出工作空间 |
| `ERR:PATH` | 目标可达，但直线路径中途穿出工作空间 |
| `ERR:LONG` | 单行超过 64 字节，整行丢弃 |
| `ERR:BUSY` | **3.0** 正在回放或正在运动，该指令此时不接受 |
| `ERR:FULL` | **3.0** 示教点已满（上限 64） |
| `ERR:EMPTY` | **3.0** 点表为空，没有可回放的内容 |
| `ERR:INDEX` | **3.0** 点序号越界 |
| `ERR:FLASH` | **3.0** Flash 擦写失败，或代码区已经占到最后一页 |

### 5.4 上电回执

上电后主动发一行 `READY 3.0`。

**用途**：串口没反应时，先按一下复位键——
- 看到 `READY 3.0` → 固件是这份、TX 通路正常，问题只在 RX 方向
- 看不到 → 烧的不是这份固件，或者 TX 接线/驱动有问题

## 6. 运动控制

实现：`Hardware/Motion/motion.c`

### 6.1 按时间推进，而不是按主循环圈数

**旧做法**：主循环每转一圈走固定 1mm。

**问题**：主循环周期根本不固定——`OLED_Update()` 一次十几毫秒，区间扫描几十毫秒。
结果末端速度随刷新节奏抖动，整体还被拖慢。

**现在**：

```c
dt = HAL_GetTick() - s_last_ms;

// 先算这一轮允许的速度（梯形剖面的核心，见 6.5）
v_lim = sqrtf(2 * MOTION_ACCEL * dist);   // 剩这么远还刹得住的最大速度
if (v_lim > s_vmax) v_lim = s_vmax;       // 也不能超过巡航速度
s_v = (s_v < v_lim) ? s_v + MOTION_ACCEL*dt : v_lim;

s_accum += s_v * dt;
if (s_accum < MOTION_STEP_MIN) return;   // 攒着，不白解逆解
```

三个保护：

| 保护 | 原因 |
|---|---|
| `dt == 0` 直接返回 | 同一毫秒被调两次 |
| `dt > 50ms` 截断 | 主循环被卡过，别一步跳好几毫米 |
| 累加器 < 0.5mm 先攒着 | 主循环很快时不为 0.05mm 反复解逆解 |

### 6.2 参数

| 宏 | 值 | 含义 |
|---|---|---|
| `MOTION_SPEED_DEFAULT` | 0.05 | 上电默认末端线速度 50mm/s（`V` 命令可改） |
| `MOTION_SPEED_MM_MIN/MAX` | 20 / 150 | 可调速度区间（mm/s） |
| `MOTION_ACCEL` | 0.5 | 末端加速度 m/s²，决定起步/刹车多猛 |
| `MOTION_STEP_MIN` | 0.0005 | 单次推进最小 0.5mm |
| `MOTION_DT_MAX_MS` | 50 | 单次 Tick 最多补 50ms |
| `MOTION_ARRIVE_EPS` | 0.0005 | 到位容差 0.5mm |
| `MOTION_COORD_LIMIT` | 1.0 | 坐标绝对值上限 1m |
| `MOTION_PATH_STEP` | 0.005 | 路径采样步长 5mm |
| `MOTION_PATH_MAX_SAMPLES` | 128 | 采样点上限 |

> `MOTION_SPEED_DEFAULT = 0.05` 仍是估值（1mm/圈 × 20Hz），但它现在**不用改代码就能改**：
> 串口发 `V 70` 立刻生效。实测时按这个流程走：
> 从 50 往上加，盯住关节有没有滞后（末端实际位置追不上 `?` 里的目标），
> 一旦开始滞后就往回退 10，记下这个值，再填回宏里当默认值。

### 6.3 三重校验（顺序有讲究）

```
1) 数值范围   → 先挡 280（毫米当米）这种笔误，不必浪费逆解
2) 终点可达   → 目标本身就不在空间里，直接拒
3) 路径可达   → 起点终点都行，但中间穿洞，也拒
```

校验通过才改目标；失败时目标和运动状态**原封不动**，不会把机械臂带偏。

**为什么第 3 步必要**：三连杆的工作空间是带洞的壳。起点和终点都可能可达，
中间却穿出不可达区——那种情况下末端会走到洞边卡住，表现是"走到一半顿一下"。

采样从 `i=1` 开始（起点不用校验）。30cm 移动约 60 次采样，按 ~30µs/次算约 2ms。

> 路径校验会让远距离遥控变"挑"（工作空间只有 66.3% 可达且非凸，斜穿边界容易回 `ERR:PATH`）。
> 嫌烦可以把 `MOTION_PATH_CHECK` 改 0，退回"只校验终点"。

### 6.4 到位回执

协议层**不自己判断到位**，只观察 `Motion_IsBusy()` 由 1 变 0 时推 `DONE`。

> 到位是运动模块算出来的事实，重复实现一遍迟早会不同步。

`s_wait_done` 只在串口受理过 `M` 之后置 1，所以按键遥控不会冒出 `DONE`。

### 6.5 梯形加减速（3.0）

**3.0 之前的问题**：`s_accum` 是纯匀速——速度从 0 直接跳到 50mm/s，到点直接停。
物理后果是启动瞬间冲击电流最大、结束时结构回弹。

> 注意范围：这里治的是**笛卡尔运动**（`M` / 按键）的起停冲击。
> [10.1](#101-已知限制) 里还有一条「夹着东西转大角度可能甩出」，
> 那是 `R` 旋转命令用 `SetAngleNow` 立即到位的固有行为，走的不是这条路径，
> 梯形加减速管不到它。

**做法**：速度不再是常数，而是被两条曲线夹住的状态量。

```
上限 A：s_vmax         —— 人设的巡航速度（V 命令可改）
上限 B：sqrt(2*a*剩余)  —— 以 MOTION_ACCEL 还能刹住的速度
实际速度 = min(A, B)，且每轮最多变化 a*dt
```

于是同一个公式自然产生三段：

| 阶段 | 现象 | 原因 |
|---|---|---|
| 加速段 | 速度被 `a*dt` 慢慢抬上去 | 剩余距离大，上限是 A |
| 匀速段 | 速度不动 | 已经顶到 A |
| 减速段 | 速度跟着上限 B 掉下来 | 剩余距离变小，B 掉到 A 以下 |

距离短的时候加速段和减速段撞在一起，梯形退化成三角形，速度还没到 A 就开始减——
这正是想要的：短距离本就该更慢。

**为什么上限用 `sqrt(2*a*d)` 而不是「按比例分配时间」**：
这个式子就是匀减速的运动学解 `v² = 2as`，它保证在剩余距离内恰好能把速度降到 0。
按比例分配只能得到「看起来像梯形」的形状，一旦巡航速度被 `V` 改掉，
减速段就可能刹不住，末端会撞一下目标点。

**为什么减速段允许速度突变**：`v_lim` 是「刹得住」的边界，贴着它走永远安全。
如果按 `-a` 慢慢减，万一目标中途被改近（按键遥控就会），就来不及——
冲过目标再被拉回来，比减速猛一点更糟。

**一个反直觉的改动**：`Motion_SetTarget` 现在**不清** `s_accum`，也**不清** `s_v`。

2.0 清累加器是为了防止「上次剩的半截位移叠到新路径上」。但那是在匀速模型下，
累加器就等于将要走的距离。现在累加器只是「不够 0.5mm 的零头」，与路径无关；
而按键遥控时目标每轮主循环都在变（一次 5mm），如果每次都清，
累加器永远攒不到 0.5mm——表现就是**按住键手臂不动**。速度同理，
每次清零等于每次从 0 重新加速，永远到不了设定速度。

**实测仿真的结果**（`a=0.5, v=50mm/s`）：300mm 用 6.07s（纯匀速是 6.00s），
5mm 单步 0.17s，全部零超调；中途改近目标、按键连发、反向回原点三种场景也都零超调。

### 6.6 纯偏航模式（3.1）

**现象**：用 `M` 改 z，肩/肘/腕会跟着一起动，看起来像「只想转个方向，结果四个关节乱动」。

**这不是 bug，是坐标定义决定的**。`z` 是**横向米数**，不是角度：
`yaw = atan2(z, x)`、`r = hypot(x, z)`（`model.c` 的 `solve`）。改 z 时偏航角和平面
半径**同时**变。末端在空间里沿**直线**横移，到基座的距离必然变长（斜边 > 直角边），
臂就必须伸缩，肩/肘/腕一起补偿。

实测（初始位姿 `x=0.28, y=0.10`，用同一份标定参数解算）：

| z (m) | 底座 | 肩 | 肘 | 腕 | r (m) |
|---|---|---|---|---|---|
| 0.000 | 90.00 | 119.78 | 69.87 | 42.09 | 0.2800 |
| 0.010 | 92.05 | 119.86 | 70.01 | 42.15 | 0.2802 |
| 0.050 | 100.12 | 121.58 | 73.17 | 43.59 | 0.2844 |
| 0.100 | 109.65 | 126.97 | 83.25 | 48.28 | 0.2973 |

10cm 横移只让半径长了 17mm，肘关节却为此动了 13.4°——因为肘离末端最近、对半径最敏感。

**做法**：新增 `Y <度>`，走柱坐标语义。进入模式时锁定当前的半径 r 与高度 h，
之后只改偏航角，俯仰三关节的逆解输入根本没变。

关键实现有三条，都是踩过坑才定下来的：

1. **不走 `model_now()`，只写底座那一路 PWM。** `model_now` 会重解三关节，
   虽然 r、h 不变时数值相同，但 `(uint16_t)` 截断在浮点尾数压线时仍可能翻 1 位。
   纯偏航的定义就是「一个舵机都不许动」，直接 `Servo_Motor_SetAngleNow(1, ...)` 才干净。
2. **r、h 在进入模式时锁定**，不每步反算。若每步都拿当前坐标开方求半径，
   浮点误差会一步步累积，转十次半径就漂了，也就回不到原点。
3. **`Motion_SetYaw` 不清角累加器**。原因同 6.5 最后一条：串口连发
   `Y 10 / Y 11 / Y 12` 时如果每轮都清，累加器永远攒不到 0.25°，表现就是
   **发了命令手臂不动**。只在首次进入模式时清。

**为什么不把 `M` 的 z 直接改成角度**：那样 x/y 是米、z 是度，`Motion_Dist`、
速度上限、路径采样全部变成量纲混合，梯形剖面算出来的就不再是速度了。
所以拆成两条命令：`M` 管「到空间里的哪个点」，`Y` 管「朝哪个方向」。

两者互斥切换：任何一条 `M` 都会退回笛卡尔模式，起点取当前所在的弧上点
（`s_cx/s_cy/s_cz` 在偏航期间一直跟着更新，所以是无缝的）。

**入口有两个**：串口指令 `Y <度>`，以及 3.0 网页左栏「转向 / 偏航」区的
`−步长` / `+步长` / `回正` 三个按钮。按钮发的是**绝对角度**（`Y 15` 不是 `Y +15`），
所以网页要自己记住当前朝向：固件 `S` 行的底座安装角减 90 就是偏航角，
收到回报就更新。点完按钮**立刻**把本地值改成目标值，否则轮询是 500ms 一次，
连点两下读到的还是旧角度，两条命令指向同一目标、手臂只转一次。命令被拒时
下一帧回报会把本地值纠正回来，不需要额外的回滚逻辑。

**仿真结果**（角速度 60°/s，角加速度 120°/s²，`eps = step = 0.25°`）：

| 场景 | 结果 |
|---|---|
| 0 → 15°，dt=20ms | 0.66s，峰值 42.9°/s，零超调 |
| 转 20° 途中改到 -10° | 不回头，末值精确 -10.00 |
| 每 20ms 连发 `Y` 递增 1° | 不卡死，正常跟随 |
| dt=1ms 极限节拍 | 0.35s 收敛 |

## 7. 夹爪与旋转

### 7.1 两个舵机，两个功能

| 舵机 | 引脚 | 功能 | 控制指令 |
|---|---|---|---|
| 5 | PA6 | **旋转**（绕末端轴转，改变夹持朝向） | `R <角度>` |
| 6 | PA7 | **开合收紧** | `G 0\|1` |

> ⚠️ 早期版本把两者设成同一角度，是错的——这两个功能完全不同。

### 7.2 开合

```c
#define GRIP_ANGLE_OPEN     0u    /* G 0 */
#define GRIP_ANGLE_CLOSE    60u   /* G 1 */
```

- 已实测确认：`G 1` → 60° = 收紧，`G 0` → 0° = 张开
- 用 `SetAngleNow` **立即到位**：走插值要 3 秒，夹爪等不起
- **回 `OK` 表示已下发，不是「夹到位」**——夹爪没有位置反馈

> 60° 夹不住就往上加；听到舵机"嗡嗡"不停说明顶死了，赶紧减。

### 7.3 旋转

- `0°` = 夹爪**平行于地面**（上电初始姿态，实测基准，**不要改**）
- `60°` = 夹爪**垂直于地面**（**实测确认**；早期按几何推论写成 90°，是错的）
- 上电时 `Servo_motor_Init()` 把它设成 0°，固定不动（除非收到 `R` 指令）

> 网页端的「垂直地面」按钮发的是 `R 60`，状态文字也按 60° 判定。
> 标定值写在 `serial_console.html` 顶部常量 `ROT_VERT_DEG`，重新标定只改那里。
>
> ⚠️ 60° 之后能不能继续转、以及 `R 180` 在物理上是什么姿态，**尚未实测**。
> 夹着工件做大幅度旋转时要慢，`R` 用的是 `SetAngleNow` 立即到位，惯性很大。

th1 = 180 − a1      th2 = a2 − 178      th3 = 90 − a3
α   = th1 + th2 + th3                   yaw = waist − 90
r   = l1·cos(th1) + l2·cos(th1+th2) + l3·cos(α)

### 8.4 示教面板（3.0）

左栏最下面是「示教 / 回放」：停留时间 + 记录、试放/循环/停止/刷新、存 Flash/推回单片机、
清空/导出/导入，再下面是由 `L` 回报渲染出来的点表，每行带一个 `×` 可以直接删。

四个实现上的注意点：

1. **连上设备时以设备为准，断联时以网页缓存为准。** `L` 回报重建的表标 `dev`，
   断联/设备空表时保留的那份标 `cache`，面板上直接写出来（"来自设备" /
   "网页缓存（设备点表为空，先「推回」）"）。缓存态下「试放」会被拦下来——
   发了也是 `ERR:EMPTY`，不如提前说清楚下一步。存储分层见 [8.6](#86-点表存在哪里31)。
2. **用 `wantList` 区分 `OK <n>` 的来源。** `T/D/C/W/P` 都回 `OK <点数>`，
   但只有前四个改了点表。发命令前设标志，收到 OK 后据此决定要不要重拉。
3. **回放期间屏蔽轮询对状态灯的覆盖。** `S` 行的 `busy` 只反映 Motion,
   回放时恒为 0；不挡住的话 500ms 后「回放 3/8」会被刷成「已到位」。
4. **「试放」发的是 `P 1`，「循环」才发 `P`。** 两个按钮分开，是因为
   这两种用法的结束条件完全不同：试放扣完一遍自动 `PLAY END`，适合验证
   点表和舵机手感；循环没有结束条件，只能 `X` 或断电。固件里 `P 0`
   等同于不带参数，所以两个入口不会串。回放期间「记录/试放/循环」会被置灰
   （固件本来就用 `ERR:BUSY` 拒），但**「停止」故意不禁**——
   万一进度回报丢了，它是唯一的人工出口。

### 8.5 3D 视图与平面点选（3.0）

中栏右上角 `2D / 3D` 切换。3D 是**手写投影**，没有引入 three.js——
整页要保持"单文件、双击即用"，为一个示意视图拖进几百 KB 的库不划算。
实际只需要三件事：绕 Y 轴偏航、抬高俯仰、透视除法。

**相机与投影**（`camBasis` / `project`）

```
视点 T = (0, 0.16, 0)                相机绕 T 在球面上转
pos = T + d·(cosφ·sinθ, sinφ, cosφ·cosθ)      θ=偏航, φ=俯仰
f = 归一化(T − pos)      前
r = (−f.z, 0, f.x) 归一化  右      u = r × f   上
屏幕 = 中心 + (focal/d)·(v·r, −v·u)          v = 点 − pos, d = v·f
```

`k = focal/d` 同时用来缩放线宽和关节圆半径，远细近粗，透视才不会像贴纸。

**平面点选**（`pickOnPlane`）是上式的逆运算：屏幕坐标先除以 `focal` 得到
视线方向 `dir = f + r·nx + u·ny`，再与水平面 `y = planeY` 求交，
`t = (planeY − pos.y)/dir.y`。自检方法是让 `project → pickOnPlane` 走一圈，
四个测试点全部回到原值（1e-6 内），说明两者没有互相跑偏。

三个设计上的取舍：

1. **取点用的是"当前目标高度"那一层，不是地面。** 手爪几乎总在某个高度上作业，
   固定取地面等于每次都要再改一次 `y`。想换层就改 `y` 再点。
2. **拖拽和单击靠位移阈值区分（3px）。** 鼠标抖动一般 1~2px，3px 既不会把慢拖
   误判成点击，也不会让正常点击失效。双击的第二下不取点（`e.detail > 1`）。
3. **工作空间底图在 3D 下置灰。** 那张图是逐点扫逆解算出来的 `(r, h)` 剖面，
   三维里没有对应物；硬投影会变成一团糊，不如明确说"这个选项在 3D 下没用"。

3D 里画的东西：桌面（±0.33m 网格，0.05m 一格）、底座盘、末端到地面的投影与虚线
（不看这条线判断不出高度）、指令目标红十字、点选留下的蓝圈、以及按视深排序的连杆。

### 8.6 点表存在哪里（3.1）

**问题**：设备一断联，面板上的示教点就没了。

**不是存储介质的问题，是断电**。这条 USB 线同时供电，拔线 = 单片机掉电，
`s_pt[]` 在 RAM 里，跟着没了。网页那张表原本是 `L` 回报的镜像，断联时被主动
清空，于是两边同时归零。就算不清空，只要数据只在网页里也放不了——**回放的
执行者是单片机**，点必须在它的 RAM 里。

所以做成三层，各管一段：

| 层 | 位置 | 生命周期 | 谁用 |
|---|---|---|---|
| RAM | 单片机 `s_pt[64]` | 掉电即失 | 回放 `P`、按键脱机启停 |
| Flash | 最后一页 `0x0800FC00` | 掉电不丢 | 上电 `Play_Init` 载回 RAM |
| 网页缓存 | 浏览器 `localStorage` | 跟浏览器走 | 断联/断电后的副本，可导出 |

**为什么网页缓存不能替代 Flash**：脱机按键回放读的是 RAM，而 RAM 的内容来自
Flash。只存网页的话，每次上电都得连电脑、等网页推完才能跑——那正好废掉了
Flash 存储唯一的价值。

**为什么必须有 `A` 命令**：`T` 只能"记当前姿态"，没法把指定角度写进去。
没有 `A`，网页缓存就是一张只能看不能用的截图。`A` 让推回变成可能：
`C` 清空 + 逐条 `A`，64 个点大约 0.3 秒。

**推回为什么要一条一条等 `OK`**：`UART_RX_BUF_SIZE` 只有 1024 字节
（`uart_app.h`），64 条 `A` 约 1.6KB，一口气倒进去必然溢出，而且**不会报错**——
中间的行被丢掉，点就少了，人还会以为推成功了。拿应答当节流阀最省事。

**踩到的三个坑**：

1. **断联分支清空 `playPoints`**（原第 1562 行）。本意是"状态不可信"，实际
   把唯一副本删了。改成保留 + 标记来源。
2. **`L END 0` 覆盖缓存**。设备点表空 == 断过电，这时清缓存等于白存。改成
   "空表不覆盖，只把来源标成 cache"，让用户自己决定推回还是丢弃。
3. **清空时 `ptSig` 置成 `"[]"`**，`saveCachedPoints` 判定"签名没变"直接返回，
   `localStorage` 的 key 没被删掉，刷新后点表"复活"。置 `null` 才对。

**网页缓存的边界**（都写进注释了）：`localStorage` 跟着浏览器和源走——
换浏览器、清站点数据、换电脑就没了，无痕窗口关掉即失；`file://` 下各浏览器
对同源判定不一致，所以读写全包在 `try` 里，失败就退化成"只在内存里"。
要跨机器带走，用「导出」（JSON，含 6 个角度 + 停留时间）。

## 9. 调试踩坑记录

> 这一节是本文档最有价值的部分。每条都是「现象 → 原因 → 修复」。

### 9.1 `r = x` 漏了 z 分量

- **现象**：`z ≠ 0` 时末端偏移最大 92.5mm
- **原因**：水平半径写成 `r = x`，忽略了横向偏移
- **修复**：`r = hypot(x, z)`
- **为什么一直没发现**：`main.c` 里 `z` 恒为 0，从没暴露

### 9.2 只取肘上解

- **现象**：大量明明够得到的点被判 `ERR:OUT`，可达率只有 44.9%
- **原因**：`th2 = +acos()` 只试了肘上构型，实物是肘下工作
- **修复**：两种构型都试，可达率 44.9% → 61.2%

### 9.3 行程检查容差过大导致静默截断

- **现象**：末端有 2.2mm 的固定误差
- **原因**：行程检查用 0.5° 容差，`a2 = 180.49°` 被判合格，随后 `clamp_servo` 钳到 180
- **修复**：容差改成 0.01°。既能吸收浮点误差，又不会产生可观的静默截断

### 9.4 不能按 IDLE 切帧

- **现象**：连发两条命令时只执行第一条
- **原因**：`Uart_FrameReady()` 反映的是"总线静默"，不是"收到换行"。
  两条命令很可能落在同一帧里，被当成一条解析失败
- **修复**：按 `\n` 切行。行缓冲天然能处理"一条命令跨两次读"和"两条命令挤在一次读"

### 9.5 不用 `strtof` / `%f`

- **原因**：newlib-nano 的浮点解析要多占 2~3KB Flash；
  `%f` 更是没开 `-u _printf_float` 会直接链接失败
- **修复**：手写 `[-]ddd.ddd` 解析；应答里的坐标一律转成整数毫米

### 9.6 `Key_Check` 的 `||` 短路

- **现象**：按一次键偶尔多走一步
- **原因**：`Key_Check(n, Flag)` 是"有标志就返回 1 并清掉"，
  `KEY_DOWN` 和 `KEY_REPEAT` 是**各自独立的一次性锁存**。
  写成 `if (Check(DOWN) || Check(REPEAT))`，DOWN 命中时 REPEAT 没被读走，
  标志滞留在 `Key_Flag` 里，下一轮又冒出来
- **修复**：`k = Check(DOWN); k |= Check(REPEAT);` 两个都读

### 9.7 关串口的顺序

- **现象**：断开后再连不上，提示"端口仍被锁"
- **原因**：`port.close()` 之前读循环还没退干净
- **修复**：`reader.cancel()` → **等读循环 promise 结束** → `writer.releaseLock()` → `port.close()`

### 9.8 错误提示被轮询冲掉

- **现象**：收到 `ERR:PATH`，状态灯变红，但 500ms 后轮询回来就被刷成"已到位"
- **修复**：加 `errLock`，报错后锁住状态灯，下次发送才解锁

### 9.9 `x < 0` 静默出错

- **现象**：发 `M -0.28 0.10 0`（目标在背后），机械臂甩到正侧面，串口还回 `OK`
- **原因**：`solve()` 里 `waist = clamp_servo(atan2(z,x)·R2D + 90)` **只钳位不检查**，
  而 a1/a2/a3 都有行程检查。`x < 0` 时 `waist_raw` 超出 `[0,180]`，被静默压到 0 或 180，
  而俯仰解算用的是 `r = hypot(x,z)`（恒为正），照样成功 → 判为"可达"
- **修复**：`solve()` 开头加 `if (waist_raw < -0.01 || waist_raw > 180.01) return 1;`

### 9.10 肘补偿方向搞反（182 → 178）

- **现象**：用户说"舵机三会往下偏两度"，第一次把 `ZERO_A2` 从 180 加到 182，结果"方向反了"
- **诊断线索**：用户报 `M 0.28 0.10 0` 时 OLED 显示 `E=180`。
  先确认 `Servo_motor_Init()` 默认值是 **90**（不是 180），所以 180 只能是 a2 被钳位；
  而 `a2 = 182` 恰好只出现在 `th2 = 0`（完全伸直）
- **真正含义**：用户说的"往下偏"是**"需要往下调"**（实际偏高），不是"实际偏低"
- **修复**：`ZERO_A2` 改成 **178**（少给 2°，让小臂往下）。
  同时 a2 行程上限保持 180——若放宽到 182，`th2 ∈ [0,4°]` 的**肘上构型会被误接受**
- **教训**：中文"往下偏"有歧义，必须追问是"实际偏了"还是"需要往哪边调"

### 9.11 PA6 / PA7 功能混淆

- **现象**：`G 1` 时夹爪动作不对
- **原因**：代码把两个舵机设成同一角度，以为它们是"两个手指"。
  实际 **PA6 是旋转爪子、PA7 是开合收紧**，功能完全不同
- **修复**：`G` 只驱动 PA7；PA6 单独用 `R` 指令控制

### 9.12 改上电初始姿态要谨慎

- **现象**：把 PA6 从 0° 改到 90°（想"取中位更安全"），结果夹爪歪了
- **原因**：0° 是实测标定的"夹爪平行于地面"基准，不是随便一个位置
- **修复**：改回 0°
- **教训**：舵机上电会朝 PWM 对应角度弹过去，初始值选错不仅姿态歪，还可能撞结构

### 9.13 无头截图的窗口高度 ≠ 实际视口

- **现象**：按 1366×768 截图看着够用，实际打开还要滚动
- **原因**：无头模式没有浏览器 UI，视口就是 768px；
  真实浏览器地址栏+标签栏要吃掉约 100px，**实际视口只有 ~660px**
- **教训**：做响应式验证要用"真实视口高度"，否则会误判成"够了"

### 9.14 第三方库的 const 签名

- **现象**：`-Wdiscarded-qualifiers` 警告
- **原因**：`OLED_ShowString` 的签名是 `char *String`，而传的是 `const char *`
- **修复**：给 `OLED_ShowString` / `OLED_Printf` 的字符串参数加 `const`
  （实现内部只读不写，本来就该是 const）
- **⚠️ 注意**：这是江科大 OLED 库。以后重新拷贝 `OLED.c/h`，这两处 `const` 会丢

## 11. 示教与回放（3.0）

实现：`Hardware/Play/play.c` + `play.h`

### 11.1 为什么记关节角，而不是记坐标

这是整个设计里唯一需要想清楚的决定。

记坐标（`x y z`）看起来更自然，但会立刻撞上 2.0 的三个既有约束：

| 约束 | 记坐标的后果 |
|---|---|
| 工作空间只有 66.3% 可达且非凸 | 示教点必须在可达区内，摆姿态的自由度被砍掉 |
| `MOTION_PATH_CHECK` 会拒掉中途穿洞的直线 | 两个合法点之间回放，可能突然 `ERR:PATH` 走不动 |
| 单点精度 1~3cm（标定 + 舵机精度） | 回放时姿势和示教时不一致，误差还会累积 |

记角度就把这三条全部绕开了：**回放不做逆解、不做路径校验**，直接下发 6 路 PWM。
精度也从"绝对精度"退化成了"重复精度"——同一台机器回到同一组角度的偏差，
远小于标定误差。这是舵机机械臂的常规做法，不是偷懒。

**代价**：回放点只能来自示教，不能事后用坐标微调；也不能在两个示教点之间
指定"末端走直线"（关节空间插值下末端走的是弧线）。

### 11.2 数据结构与存储

```c
typedef struct {
    uint16_t a[6];      /* 舵机 1~6 的安装角 */
    uint16_t dwell;     /* 到位后停留毫秒 */
} Play_Point;           /* 14 字节，无填充 */
```

| 项 | 值 | 说明 |
|---|---|---|
| `PLAY_MAX_POINTS` | 64 | RAM 占用 64 × 14 = 896B |
| `PLAY_DEFAULT_DWELL_MS` | 500 | `T` 不带参数时的停留 |
| `PLAY_MS_PER_DEG` | 8 | 每度 8ms ≈ 125°/s，段时长按**最大关节位移**算 |
| `PLAY_MIN_SEG_MS` / `MAX` | 150 / 2000 | 小动作不拖沓，大动作不至于慢到像卡死 |

**Flash 存放**：最后一页 `0x0800FC00`（1KB 页的第 63 页）。
页内布局是 `Play_Header(12B) + 点表`，合计 908B，一页放得下，不分页。

- 头里带 `magic = "PLY3"`、`version`、`count`、对点表算的 **CRC16-CCITT**
- 校验不过就当没存过，退回空表 —— 不纠错，宁可空也不能放出一串错角度
- `Play_Save()` 开头拿链接脚本的 `_etext` 和这一页比较，代码区已经吃到这页就
  直接返回失败，**不擦**。3.1（纯偏航 + `A` 命令）后实测 `-Og` 全量构建
  `_etext = 0x0800B0A0`（Flash 49828B / 64KB ≈ 76%，RAM 7808B / 20KB ≈ 38%），
  距这页还有约 **19KB** 余量；将来功能加多了要先看这个数。
  注意 3.1 的纯偏航用 `sinf/cosf/atan2f`，把 libm 的浮点三角函数拉进来约 7KB，
  这是体积从 64.9% 跳到 76% 的主因（不是 `A` 命令，它只有几百字节）

### 11.3 时序：自己插值，不用 TIM4 那套

`Servo_Motor_Updata()` 的节奏是 1°/50ms（20°/s），转 90° 要 4.5 秒。
拿它做回放，每个点都要好几秒，没法用。

所以 `Play_Tick()` 自己在主循环里插值，每圈对 6 个关节各算一次
`from + (to − from) × s(t)`，然后 `SetAngleNow()` 下发 ——
顺便把 `OldAngle` 和 `NewAngle` 对齐，两套插值不会打架。

`s(t)` 不是线性时间，而是**梯形速度剖面**（3.0 加的，见 [11.3.1](#1131-为什么回放也要梯形剖面)）。

三个阶段：

```
运动（phase=0） → 到位贴合精确角度 → 停留（phase=1，读该点的 dwell）
    ↑                                        │
    └────── 停留结束，idx++ ─────────────────┘
                 idx 越界 → 循环（P 无参）或扣次数（P n）
```

时间用的是**绝对时刻差**（`now − phase_ms`），不是累加器：
主循环偶尔被 OLED 拖慢 10ms 也只是少走一小步，不会把误差攒起来。

### 11.3.1 为什么回放也要梯形剖面

3.0 之前 `Play_Tick` 是线性插值：`s(t) = t`，导数恒为 1。
这意味着**每段开头瞬间就到速、结尾瞬间停住**。只放一个点看不出问题，
但回放是连着几十个点跑，每段都硬起硬停，机械臂会像在抽搐，
而且每次起停的冲击会叠加到结构上。

改成梯形后 `s'(0) = s'(1) = 0`，起止速度都为零。

推导（记加速段占比 `r`）：速度三角形面积必须等于总位移 1，
`r/2 + (1−2r) + r/2 = 1−r`，所以匀速段的归一化速度是 `v_peak = 1/(1−r)`。
分段积分得到三段式子（`d = 2r(1−r)`）：

```
t < r      : s = t² / d
r ≤ t ≤ 1−r: s = r²/d + (t−r)/(1−r)
t > 1−r    : s = 1 − (1−t)² / d
```

> 匀速段的常数项是 `r²/d`，不是 `r/d`。写成 `r/d` 会大 `1/r` 倍，
> 接缝处位置会跳一下——实现时踩过这个坑，校验方法是代 `t=r` 看两段是否相等。

数值校验（`r = 0.25`）：`s(0)=0`、`s(1)=1`、`s(0.25)=s(0.75)=0.1667/0.8333`、
接缝左右极限一致、全程单调、端点速度 ≈ 0、中段速度 1.333 与理论 `1/(1−r)` 吻合。

**代价**：峰值角速度是平均值的 `1/(1−r)` 倍（0.25 时是 1.33 倍）。
所以**不要**为了「看起来变快」再把 `PLAY_MS_PER_DEG` 减小，
否则峰值反而超过原来那版匀速直冲的速度。

### 11.4 与 Motion 的冲突：三个必须处理的地方

**① 回放结束后必须重新同步坐标。**
回放绕过了 `model_now()`，`motion.c` 里的 `s_cx/s_cy/s_cz` 还停在回放前的位置。
不同步的话，下一条 `M` 会从那个**过期的起点**算直线和路径校验，第一步猛地一拽。

解决：`model.c` 加了正解 `model_fk()`（与逆解共用同一份标定参数），
`motion.c` 加了 `Motion_SyncFromCurrent()`，在回放结束（`Play_EndRound`）
和**中途停止**（`Play_Stop`）时都会调一次。
它读的是 `OldAngle`（实际位置），不是 `NewAngle`（目标）——停在中途时两者不同。

> 正解自检：`a1=180, a2=178, a3=90, waist=90` → `(0.36, 0.08, 0)`，与逆解的参照点一致。

**② 回放期间拒绝 `M`（`ERR:BUSY`）。**
两个模块都在写同一批 PWM，同时生效的话手臂会在两条控制律之间来回拉，
最后停在哪取决于谁后写——属于"看着能跑、其实不可复现"的 bug。

**③ 回放期间按键照读不照做。**
`main.c` 里按键块用 `go &&` 门控执行，但 `Key_Check` 仍然逐轮调用。
不读的话 `Key_Flag` 会一直锁存，回放一结束四个键的 DOWN 标志一次性全触发，
手臂朝某个方向连跳好几步。

### 11.5 事件回执

回放的状态**不塞进 `S` 行**——`S` 的 11 字段契约是给所有上位机的，
为了一个新功能改公共格式不划算。改用独立事件：

```
PLAY 3/8     进入第 3 个点（共 8 个）
PLAY END     整轮结束（单次跑完，或次数用尽）
```

`play.c` 只把事件挂起来，`Protocol_Poll()` 取走后翻成文本 ——
"谁能往串口写"仍然只有协议层一个出口。

### 11.6 已知限制

| 限制 | 说明 |
|---|---|
| 只能放示教过的姿态 | 关节空间回放，不能用坐标在回放中微调 |
| 末端轨迹是弧线 | 关节线性插值不保证末端走直线；有避障需求要自己加点 |
| 回放速度不跟 `V` 走 | `V` 只改笛卡尔运动速度；回放速度由 `PLAY_MS_PER_DEG` 定死，改它要重新编译 |
| 无急停按钮 | `X` 只能从串口发；硬件急停还是得靠断电 |
| 断电不知道停在哪 | 上电仍回初始位姿，不会续上刚才的回放 |
| Flash 只有一页 | 存新的会覆盖旧的，没有多套程序的概念 |

### 11.7 按键启停回放（3.0）

存进 Flash 之后，**不接串口也能跑**：按住 `KEY_3` + `KEY_4` 约 20ms 触发。

| 状态 | 按组合键 | 结果 |
|---|---|---|
| 静止、点表非空 | 按住 | `Play_Start(0)` 无限循环 |
| 正在回放 | 按住 | `Play_Stop()` 停在当前姿态 |
| 点表为空 | 按住 | 无反应（Flash 没存过，或刚发过 `C`） |
| 正在走 `M` | 按住 | 不启动，等到位后再按 |

**为什么用两个键的组合，而不是单击某个键**：四个键已经分给 `x+/x-/y+/y-`，
单击要留给微调，不能挪用。长按也不行——`KEY_LONG` 和微调的长按连发是同一个事件，
长按 `KEY_4` 会先连续微调 `y-` 再触发回放，手臂已经跑出去一段了。
所以只能找一个"正常操作绝不会做"的动作。

**实现要点**

```c
combo_now = Key_Check(KEY_3, KEY_HOLD) && Key_Check(KEY_4, KEY_HOLD);
if (combo_now && !combo_prev) { ...触发... }   // 自己做边沿检测
combo_prev = combo_now;
```

- 用 `KEY_HOLD` 而不是 `KEY_DOWN`：`HOLD` 是电平量，`Key_Check` 读它不会清除
  （`Key.c` 里 `if (Flag != KEY_HOLD)` 那个分支），所以每轮都能重新查，
  能凑出「两键同时按着」；`DOWN` 读一次就没了，拼不出组合。
- `HOLD` 按着不动一直是 1，不做 `combo_prev` 边沿的话会每 20ms 翻转一次启停。
- 触发时把两键本轮的 `DOWN`/`REPEAT` 清掉，并把 `go` 置 0，
  否则按住等手臂停下的那段时间里 `KEY_REPEAT` 会每 100ms 送一次微调。

**已知副作用**：组合是分两次按下的，中间至少隔一个 20ms 扫描周期，
先按的那个键会先走一次 5mm 微调（按住超过 500ms 还会进入连发）。
实际无害——回放下行的是**绝对角度**，第一个点立刻会把这丁点偏移纠正回来。

> 想彻底消掉这个副作用只能加第 5 个独立按键。`Key` 模块已经支持 `KEY_5`
> （`#ifdef KEY5_Pin` 那段），改 `.ioc` 加个引脚就行，不需要动这里的代码。

开关在 `main.c` 顶部：`PLAY_KEY_ENABLE`（0 关闭，回放只能用串口 `P`/`X`）、
`PLAY_KEY_ROUNDS`（默认 0 = 无限循环，改成 1 就是按键按一次放一遍）。

### 11.8 验证步骤

```
?                 → S ... 一个正常状态
M 0.28 0.10 0     → OK → DONE
T                 → OK 1        第 1 点记下
M 0.36 0.08 0     → OK → DONE

（按复位）         → READY 3.0
L                 → L END 2     点表还在
D 2               → OK 1
C                 → OK 0
```
